# План: перевод Lucky's Learning World на разработку внешними агентами

**Дата**: 2026-07-28
**Автор**: Claude Code (аудит + план)
**Статус**: черновик на утверждение
**Цель**: любой внешний агент, у которого есть только ссылка на GitHub Issue и доступ к репозиторию, должен суметь закрыть задачу сам — без доступа к машине `D:\SD`, без вопросов в чат, без риска сломать то, чем пользуется Lucky и её одноклассники.

## 0. Резюме для человека (одна страница)

**Что происходит сейчас.** Задачи живут в markdown-файлах внутри репозитория (`tasks/*.md` + `tasks/INDEX.md` + самописный `scripts/sync-issues.mjs`). GitHub Issues — это пустые заголовки-огрызки: issue #1 и #2 открыты, хотя обе задачи давно `RELEASED`. Веток нет, PR за всю историю — ноль, всё пушится прямо в `master`, и каждый push сразу уезжает в прод. Правила для агентов написаны с абсолютными путями вида `file:///d:/SD/...`, которые для внешнего агента не существуют.

**Почему это не даёт то, что вам нужно.** Внешний агент (ChatGPT с доступом к GitHub, Claude Code в VSCode по ссылке на issue) видит **только GitHub**. Он не видит `tasks/TASK-004.md`, пока не склонирует репо и не догадается туда заглянуть. Он не может «предложить» изменение, потому что не существует пути PR → проверка → мерж. И он не может ошибиться безопасно, потому что любая запись в `master` мгновенно становится продом.

**Что нужно сделать.** Пять сдвигов, в этом порядке:

1. **Контракт в репозитории.** `AGENTS.md` переписать как рабочий контракт (как в `agent-orchestrator`): относительные пути, точные команды, явный список запретов. Плюс тонкие указатели `CLAUDE.md`, `.cursorrules`, `.windsurfrules`, `.github/copilot-instructions.md`.
2. **CI на PR + branch protection + автомерж.** Сейчас тесты гоняются только при push в `master`. Нужны проверки на pull request, запрет прямого push, автомерж при зелёном CI.
3. **Два канала прода.** `/` — **stable** (то, чем реально играют), `/next/` — **автоматически** из `master`. Stable двигается только вашей командой «выкатить 2.0.4 как стабильную». Именно это делает автомерж безопасным: агент мержит в `master`, но до детей это не доезжает.
4. **Трекер в GitHub Issues + Projects.** `tasks/`, `sync-issues.mjs`, `task-new.mjs`, корневой `ACCEPTANCE_CRITERIA.md` — удалить. Acceptance Criteria переезжают в тело issue.
5. **Уборка корня.** 7 больших брифов, дубли `implementation_plan.md`/`walkthrough.md` и — главное — физические копии всего приложения в `v1/` и `v2/` (254 и 231 файл в git). Это самая опасная ловушка для параллельных агентов.

**Ключевая мысль по вашему требованию про мерж.** Вы просили автомерж при зелёном CI и одновременно чтобы старая версия на проде не двигалась. Это не два требования, а одно решение: `master` становится «быстрым» каналом с автомержем, а `stable` — отдельным указателем, который двигается только вами. Автомерж перестаёт быть рискованным ровно потому, что прод для детей от него отвязан.

**Сколько это стоит.** Этапы 0–2 — примерно один вечер вашей работы плюс агент. Этап 3 (каналы) — самый содержательный, полдня-день. Этапы 4–5 можно и нужно отдать уже внешнему агенту — это заодно проверка, что конвейер работает.

Проект Lucky к harness не подключён вовсе (`.agents/` и `.claude/` в нём отсутствуют, `AGENTS.md` написан руками). Подключать сейчас смысла нет — выгода нулевая, пока `harness/skills` пуст. Это отдельная задача на потом.

### 1.2 Репозиторий Lucky — что хорошо

- **Zero-build архитектура** (ванильные ES-модули, никакого Webpack/Vite). Для агентов это огромный плюс: нечему ломаться в тулчейне, `npm ci` нужен только для тестов.
- **Настоящий CI-гейт**: `deploy.yml` запускает `npm run test:coverage:gate` (65% строк / 60% ветвей / 60% функций) **до** деплоя на Pages. Последние 5 прогонов зелёные.
- **13 тестовых файлов** на нативном `node --test`, тесты помечены `@task` / `@ac`.
- Дисциплина «сначала Acceptance Criteria» уже принята и описана в `DEVELOPMENT_RULES.md`.
- Репозиторий публичный, Issues включены.

Это хорошая база. Ломать её не нужно — нужно развернуть её наружу, в GitHub.

### 1.4 `AgentWrapper/agent-orchestrator` — что именно делает его пригодным для внешних агентов

Разобрал репозиторий по частям. Работает не «магия», а конкретный набор артефактов:

| Артефакт | Что делает | Есть у Lucky? |
|---|---|---|

| `CONTEXT.md` | Глоссарий домена. Только термины, без решений | Нет |
| `CONTRIBUTING.md` | Протокол «застолби задачу»: комментарий в issue → ждёшь назначения → один issue = один PR | Нет |
| `.github/ISSUE_TEMPLATE/*.yml` (Issue Forms) | Структурированные поля с `validations: required` — репорт нельзя отправить пустым | Один `task.yml`, не закоммичен |
| `.github/pull_request_template.md` | Разделы What / Why / How / Testing + чеклист со ссылкой на `AGENTS.md` | Нет |
| Таксономия меток | `P0`/`P1`/`P2`, `comp/daemon`, `comp/cli`, `comp/desktop`, `needs-triage`, `blocked`, `good first issue`, `help wanted` | Стоковые метки GitHub |
| ~16 workflow'ов, **срабатывающих на PR** | Проверки по областям, а не одна общая | Один `deploy.yml` только на push |
| `docs/architecture.md`, `docs/STATUS.md`, `docs/adr/` | «Что уже в main, а что в полёте» + записанные архитектурные решения | Нет |

Отдельно: сам продукт AO (изоляция агентов по git-worktree, обратная связь от CI и ревью) у вас **установлен** — `~/.ao`, версия 0.10.2, поставлен 2026-07-11 — но фактически не используется: зарегистрирован один проект `personal` с путём `D:\Google Drive\Personal`, сессий 0, PR 0. Это потенциальный второй слой (Этап 6), но для вашей цели он **не требуется**: ChatGPT и Claude Code в VSCode ходят через GitHub, а не через AO.

**Главный вывод из сравнения.** Разница между Lucky и agent-orchestrator — не в объёме кода и не в инструментах. Она в том, что у AO **точка входа для агента — это GitHub**, и всё нужное для работы доступно оттуда. У Lucky точка входа — ваша файловая система. План ниже целиком про перенос точки входа.

## 2. Целевая картина

```
                    вы: идея → ревью плана → Issue (шаблон + AC) → метка agent-ready
                                          │
        ┌─────────────────────────────────┼─────────────────────────────────┐
        ▼                                 ▼                                 ▼
  ChatGPT с доступом            Claude Code в VSCode              любой другой агент
     к GitHub                    (дали ссылку на issue)             (Cursor, Codex…)
        │                                 │                                 │
        └─────────────────────────────────┼─────────────────────────────────┘
                                          ▼
                       ветка issue-<N>-<slug> → PR «Fixes #N»
                                          ▼
                        CI на PR: тесты + coverage + версии + гигиена
                                          ▼
                          зелено → автомерж (squash) в master
                                          ▼
                    Pages: /next/  ← обновляется автоматически, всегда
                           /       ← stable, стоит на теге `stable`
                                          ▼
                    вы: «выкатить 2.0.4 как стабильную» → тег двигается → /
```

Что вы делаете руками в этой схеме: формулируете issue, ревьюите план (если нужно), жмёте «выкатить в stable». Всё остальное — агенты и CI.

## 3. План по этапам

### Этап 0 — Стыковка с идущей работой по TASK-003 (человек, 15 минут)

**Зачем.** TASK-003 «GitHub External AI Agent Ecosystem» **выполняется прямо сейчас** другим агентом. Его рабочее дерево — тот же каталог: незакоммичены `CLAUDE.md`, `.cursorrules`, `.windsurfrules`, `.github/copilot-instructions.md`, `.github/ISSUE_TEMPLATE/task.yml`, `.github/workflows/agent-ci.yml`, `.github/workflows/sync-tasks.yml`, `tests/github-agent-ecosystem.test.mjs`, плюс правки в `ACCEPTANCE_CRITERIA.md`, `implementation_plan.md`, `tasks/INDEX.md`. Этот план **не должен** трогать эти файлы, пока TASK-003 не завершён, иначе два агента передерутся за одно дерево.

**TASK-003 решает примерно ту же задачу и частично пересекается с этим планом.** Карта пересечений:

| Артефакт TASK-003 | Отношение к плану | Что с ним делать |
|---|---|---|
| `CLAUDE.md`, `.cursorrules`, `.windsurfrules`, `.github/copilot-instructions.md` | **Совпадает** с Этапом 1 | Оставить как есть, Этап 1 их не переписывает — только выверяет, что они ссылаются на обновлённый `AGENTS.md` |
| `.github/workflows/agent-ci.yml` | **Совпадает** с Этапом 2 — единственное место, где появляется триггер `pull_request` | Оставить, на Этапе 2 расширить джобами `version-check` и `hygiene` и переименовать в `ci.yml` |
| `.github/ISSUE_TEMPLATE/task.yml` | **Пересекается** с Этапом 4, но полей мало и нет AC как обязательного поля | Оставить, на Этапе 4 заменить на `feature.yml` / `bug.yml` / `chore.yml` |
| `.github/workflows/sync-tasks.yml` | **Противоречит** плану: закрепляет markdown-трекер, который Этап 4 убирает | Дать TASK-003 доехать, затем удалить на Этапе 4 |
| `tests/github-agent-ecosystem.test.mjs` | **Частично противоречит**: проверяет существование `tasks/` | Дать доехать, на Этапе 4 переписать проверки под GitHub-трекер |

**Что делать.**

1. **Дождаться завершения и коммита TASK-003.** Не начинать Этап 1 на грязном дереве. Правило TASK-003 требует от агента автокоммита по завершении, так что ждать нужно именно факта коммита.
2. После коммита — зафиксировать точку старта: `git status --short` пуст, `git log -1` показывает коммит TASK-003.
3. Закрыть issue #1 и #2 (задачи `RELEASED` с 2026-07-28), в комментарии — ссылка на релиз.
4. Открыть issue на этот план (Этапы 1–5) и явно пометить, что он **надстраивает** TASK-003, а не отменяет его: TASK-003 даёт адаптеры агентов и проверку на PR, план добавляет то, чего в нём нет — защиту ветки, автомерж, два канала прода и перенос трекера в Issues.

**Предупреждение о конфликте.** Пока TASK-003 в работе, единственный файл, который этот план добавил в репозиторий, — сам документ `docs/plans/2026-07-28-external-agent-platform.md`. Он не пересекается ни с одним файлом TASK-003.

**Готово, когда**: TASK-003 закоммичен, `git status --short` пуст, открытых issue про уже сделанные задачи нет.

### Этап 2 — PR-конвейер: проверки, защита ветки, автомерж (человек + агент, ~2 часа)

**Зачем.** Сейчас «зелёный CI до мержа» невозможен: проверки бегут только после push в `master`, когда уже поздно.

**Что делать.**

1. **`.github/workflows/ci.yml`** (на базе незакоммиченного `agent-ci.yml`), триггеры `pull_request` + `push: master`. Джобы:
   - `test` — `npm ci`, `npm run test:coverage:gate`
   - `version-check` — версия во всех местах совпадает с `package.json` (см. Этап 3)
   - `hygiene` — нет новых файлов в корне (allow-list), нет `file:///`, нет `node_modules/` в диффе
2. **Branch protection на `master`** (для публичных репозиториев бесплатно, через Rulesets):
   - PR обязателен, прямой push запрещён **всем, включая вас**
   - Обязательные проверки: `test`, `version-check`, `hygiene`
   - Требовать актуальности ветки перед мержем
   - Включить в настройках репозитория **Allow auto-merge** и **Automatically delete head branches**
3. **`.github/workflows/auto-merge.yml`**: на `pull_request` с меткой `agent` (или на все PR — на ваш выбор) выполняет `gh pr merge --auto --squash`. GitHub домержит сам, когда проверки позеленеют.
4. **Метки**: завести таксономию по образцу AO — `P0`/`P1`/`P2`, `area/engine`, `area/content`, `area/ui`, `area/ci`, `area/docs`, `needs-triage`, `blocked`, `agent-ready`, `agent`, `good first issue`.

**Важное следствие, которое надо принять осознанно.** После этого этапа вы сами тоже не сможете пушить в `master` напрямую. Быстрая правка станет: ветка → PR → автомерж (это ~2 минуты, CI сейчас идёт 25 секунд). Альтернатива — оставить себе admin bypass, но тогда часть смысла защиты теряется. Рекомендую полный запрет: с автомержем скорость почти не страдает.

**Готово, когда**: попытка `git push origin master` отклоняется; тестовый PR с однострочной правкой мержится сам после зелёного CI, ветка удаляется автоматически.

### Этап 3 — Два канала прода: `stable` и `next` (человек + агент, ~полдня; самый рискованный)

**Зачем.** Ваше требование: старая версия работает и не двигается, новая обновляется автоматически, старая — только по команде. Плюс это то, что делает автомерж безопасным. Сейчас вместо этого в git лежат две физические копии приложения (`v1/`, `v2/`), которые надо руками поддерживать в согласии.

**Дизайн.**

| Адрес | Что | Как обновляется |
|---|---|---|
| `https://<pages>/` | **stable** — то, чем играют Lucky и одноклассники | Только когда вы двигаете git-тег `stable` |
| `https://<pages>/next/` | **next** — текущий `master` | Автоматически при каждом мерже |

Источник истины один — дерево в корне репозитория. Никаких копий в git. Разделение делает workflow сборки:

```
deploy.yml (на push в master и на promote):
  checkout master        → копирует в _site/next/
  checkout тега stable   → копирует в _site/
  upload-pages-artifact _site → deploy-pages
```

`promote-stable.yml` (`workflow_dispatch`, вход `version`):
1. Проверяет, что тег `v<version>` существует и его CI был зелёным
2. Переставляет тег `stable` на него
3. Запускает `deploy.yml`

Тогда «задеплоить 2.0.4 как стабильную» = одна команда:
`gh workflow run promote-stable.yml -f version=2.0.4`

**Сопутствующие работы этого этапа (без них каналы не поедут):**

1. **Удалить `v1/` и `v2/`** из git (485 файлов). Перед удалением — тег `archive/v1-v2-snapshot`, чтобы история осталась достижимой.
2. **Единый источник версии.** `package.json` — единственная правда. Скрипт `npm run version:sync` записывает её в `app.js` (`APP_VERSION`), `sw.js` (`CACHE_NAME`), `manifest.json`. Из `index.html` хардкод версии убрать — подставлять из `APP_VERSION` в рантайме (сейчас там ещё и три разных значения). `npm run version:check` в CI падает при расхождении.
3. **Переписать `scripts/release.mjs`**: убрать глобальную регулярку по `index.html` (она перепишет любое `vX.Y.Z` в тексте страницы). Релиз = bump в `package.json` + `version:sync` + тег + запись в `CHANGELOG.md`.
4. **Service Worker и области видимости.** SW, зарегистрированный на `/sw.js`, имеет scope `/` и накроет собой `/next/`. Регистрацию сделать относительной (`register('sw.js', { scope: './' })`), чтобы страница под `/next/` контролировалась своим SW. `CACHE_NAME` обязан содержать версию (уже так). Стратегия network-first сохраняется — она смягчает промахи при первой загрузке.
5. **Переключатель каналов в UI**: в модалке настроек ссылка «Try the next version» / «Back to stable». Заменяет нынешнюю самодельную кросс-версионную навигацию по `v1/`/`v2/`.

**Риски.** У пользователей уже стоит SW с прежним `CACHE_NAME`, и корень `/` меняет смысл (был «самое свежее», станет «стабильное»). Разово возможен показ старого контента до обновления SW. Смягчение: промоутнуть в stable ровно текущую живую версию **до** удаления `v1/`/`v2/`, чтобы для играющих ничего визуально не изменилось.

**Готово, когда**: `/` и `/next/` открываются и показывают разные номера версий; мерж PR меняет только `/next/`; `gh workflow run promote-stable.yml -f version=X.Y.Z` двигает `/`; `v1/` и `v2/` в git отсутствуют.

### Этап 4 — Трекер переезжает в GitHub Issues + Projects (агент, ~2 часа)

**Зачем.** Это и есть ответ на «дальше начинается строительство велосипедов». `sync-issues.mjs`, `task-new.mjs`, `INDEX.md`, `sync-tasks.yml` — 300+ строк самописного кода, который воспроизводит то, что GitHub умеет из коробки и, главное, показывает наружу.

**Что делать.**

1. **Issue Forms** вместо одного `task.yml`:
   - `feature.yml` — поля: Контекст и зачем; **Acceptance Criteria** (по одному на строку, формат `AC-1: …`, `required`); Затронутые области (dropdown → метка `area/*`); Как проверить; Ограничения и что трогать нельзя; Целевой канал
   - `bug.yml` — шаги воспроизведения, ожидаемое/фактическое, версия (`/` или `/next/`), устройство
   - `chore.yml` — техдолг, документация, CI
   - `config.yml` — ссылки на `AGENTS.md` и `CONTRIBUTING.md`
2. **В хвост каждого шаблона — блок «Контракт агента»** (фиксированный текст в `.yml`): прочитай `AGENTS.md`; ветка `issue-<N>-<slug>`; прогони `npm run test:coverage:gate`; добавь тест с тегом `@issue <N>`; открой PR с `Fixes #<N>`; не трогай перечисленное в «Жёстких правилах».
3. **GitHub Project (v2)**, колонки: `Backlog` → `Ready for agent` → `In progress` → `In review` → `Done`. Метка `agent-ready` = «сформулировано достаточно, агент может брать без вопросов».
4. **Definition of Ready** (в `CONTRIBUTING.md`): у issue есть хотя бы один `AC-*`, указана область, указано как проверить результат, нет открытых вопросов к вам. Без этого метка `agent-ready` не ставится.
5. **Миграция**: три файла `tasks/*.md` → issues с полным телом и AC. TASK-001 и TASK-002 закрыть как выполненные (см. Этап 0). «Backfill AC tags for legacy test suites» — открыть как живой issue. TASK-003 закрыть как поглощённый этим планом.
6. **Удалить**: `tasks/` целиком, `scripts/sync-issues.mjs`, `scripts/task-new.mjs`, `.github/workflows/sync-tasks.yml`, корневой `ACCEPTANCE_CRITERIA.md`, корневые `implementation_plan.md` и `walkthrough.md`. Из `package.json` убрать скрипты `task:new` и `task:sync`.
7. **Сохранить как архив**: `docs/plans/`, `docs/walkthroughs/`, `docs/releases/` — не удалять, но перестать требовать по каждой задаче. История релизов дальше собирается из заголовков PR в `CHANGELOG.md`.
8. **Связь тестов с задачами**: тег в тестах меняется с `@task TASK-XXX` на `@issue <N>`. Старые теги оставить как есть — переписывать историю не нужно.

**Готово, когда**: `tasks/` нет; новый issue создаётся через форму и содержит AC в теле; внешний агент по одной ссылке на issue получает всё нужное, ничего не спрашивая.

**Готово, когда**: в корне остаются только `README.md`, `AGENTS.md`, `CONTEXT.md`, `CONTRIBUTING.md`, `CHANGELOG.md`, `LICENSE`, адаптеры агентов, `index.html`, `styles.css`, `themes.css`, `app.js`, `sw.js`, `manifest.json`, `telemetry.js`, `reporter.js`, `package*.json`, точечные файлы. ## 4. Проверка, что всё заработало

Прогоняется после Этапа 5. Это и есть настоящий критерий приёмки плана.

1. Вы создаёте issue через форму: «На экране результатов Word Realm кнопка Next перекрывается на iPhone SE», с `AC-1` и `AC-2`, метка `agent-ready`.
2. Даёте ссылку **ChatGPT с доступом к GitHub**: «закрой этот issue». Он должен сам: найти `AGENTS.md`, понять запреты, сделать ветку, поправить, добавить тест с `@issue N`, открыть PR с `Fixes #N`.
3. Параллельно даёте другой issue **Claude Code в VSCode** одной ссылкой. Оба PR не конфликтуют.
4. CI зеленеет, автомерж срабатывает, ветки удаляются.
5. `/next/` показывает исправление. `/` не изменился.
6. Вы говорите «выкатить 2.0.4 как стабильную» → одна команда → `/` обновился.

Ни на одном шаге агент не задаёт вопросов, ответ на которые есть только на вашей машине. Это и есть цель.

**Числовые ориентиры**: 0 прямых push в `master`; ≥90% PR мержатся без вашего вмешательства кроме автомержа; `stable` двигается только по вашей команде; время «issue → мерж» < 30 минут.

## 6. Что этот план сознательно НЕ делает
