# План: перевод Lucky's Learning World на разработку внешними агентами

**Дата**: 2026-07-28
**Автор**: Claude Code (аудит + план)
**Статус**: черновик на утверждение
**Цель**: любой внешний агент — свой или принадлежащий приглашённому участнику — имея только ссылку на GitHub Issue, должен суметь закрыть задачу сам: без доступа к машине `D:\SD`, без вопросов в чат, без риска сломать то, во что играют дети.

**Принятые решения** (зафиксированы 2026-07-28):

| Решение | Значение |
|---|---|
| Кто пишет код | **Только агенты.** Владелец не пушит вручную никогда |
| Скорость | Изменения агентов должны попадать на `next` **как можно быстрее** |
| Stable | Переключение прода для детей — **по отдельной команде** |
| Приватность | Нужна **свобода действий** (снести все issues и начать заново, переиграть версии, переписать историю), а не сокрытие кода |
| Топология | Одна ветка `master` + тег `stable` |
| Хостинг | Приватный исходник + публичный репозиторий сайта |
| Трекер | GitHub Issues + Projects; `tasks/*.md` убираются |
| Участники | Дальше подключаются **другие пользователи GitHub**, которые вносят вклад своими агентами |

## 0. Резюме для человека (одна страница)

**Что происходит сейчас.** Задачи живут в markdown-файлах внутри репозитория (`tasks/*.md` + `tasks/INDEX.md` + самописный `scripts/sync-issues.mjs`). GitHub Issues — пустые заголовки-огрызки: #1 и #2 открыты, хотя обе задачи давно `RELEASED`. Веток нет, PR за всю историю — ноль, всё пушится прямо в `master`, и каждый push сразу уезжает к детям. Правила для агентов написаны с абсолютными путями `file:///d:/SD/...`, которых для внешнего агента не существует.

**Почему это не даёт нужного.** Внешний агент — ChatGPT с доступом к GitHub, Claude Code в VSCode по ссылке на issue, агент приглашённого участника — видит **только GitHub**. Он не видит `tasks/TASK-004.md`, пока не склонирует репо и не догадается туда заглянуть. Он не может «предложить» изменение, потому что пути PR → проверка → мерж не существует. И он не может ошибиться безопасно, потому что любая запись в `master` мгновенно становится продом для детей.

**Что делаем.** Шесть сдвигов, в этом порядке:

1. **Контракт в репозитории.** `AGENTS.md` переписать как рабочий контракт (по образцу `agent-orchestrator`): относительные пути, точные команды, явный список запретов. Плюс тонкие указатели `CLAUDE.md`, `.cursorrules`, `.windsurfrules`, `.github/copilot-instructions.md`.
2. **PR-конвейер.** Проверки на pull request (сейчас их нет вовсе) и автомерж при зелёном CI — это и есть «как можно быстрее на next».
3. **Приватный исходник + публичный сайт + два канала.** `/` — **stable**, `/next/` — автоматически из `master`. Stable двигается только по вашей команде.
4. **Трекер в GitHub Issues + Projects.** `tasks/`, `sync-issues.mjs`, `task-new.mjs`, корневой `ACCEPTANCE_CRITERIA.md` — удалить. Acceptance Criteria переезжают в тело issue.
5. **Уборка корня.** 7 больших брифов, дубли `implementation_plan.md`/`walkthrough.md` и физические копии всего приложения в `v1/` и `v2/` (254 и 231 файл в git).
6. **Модель доступа для приглашённых участников.** Их агенты работают через форки и PR, автомерж включается меткой, ставить которую могут только доверенные. Технически, без платного плана.

**Про скорость — упрощение, а не потеря.** Раз вручную не пушит никто, никакого «быстрого пути в обход PR» держать не нужно. Единственный путь для всех: ветка → PR → зелёный CI → автомерж → `master` → `/next/` через ~60 секунд. Дети при этом остаются на `stable`, который не сдвинется, пока вы не скажете. Автомерж безопасен ровно потому, что прод детей от него отвязан.

**Про приватность — это про свободу, а не про секретность.** Вы сформулировали точно: ценность в возможности в любой момент снести все issues и начать заново, переиграть схему версий, переписать историю — не имея аудитории, форков и людей, которые на это завязались. Zero-build означает, что игровой JS всё равно виден в DevTools, и это нормально: прятать его не нужно и не планируется. Побочная выгода приватного исходника — **allow-list того, что вообще уезжает на прод**. Это не косметика: сейчас `deploy.yml` публикует путь `'.'`, то есть публично раздаются `COMIC_THEME_AGENT_BRIEF.md`, `DEVELOPMENT_RULES.md`, `tasks/` и `docs/plans/`.

### 1.2 Репозиторий Lucky — что хорошо

- **Zero-build архитектура** (ванильные ES-модули, ни Webpack, ни Vite). Для агентов огромный плюс: нечему ломаться в тулчейне, и приглашённому участнику не нужно настраивать окружение.
- **Настоящий CI-гейт**: `deploy.yml` запускает `npm run test:coverage:gate` (65% строк / 60% ветвей / 60% функций) **до** деплоя. Последние 5 прогонов зелёные, каждый ~25 секунд.
- **13 тестовых файлов** на нативном `node --test`, тесты помечены `@task` / `@ac`.
- Дисциплина «сначала Acceptance Criteria» принята и описана в `DEVELOPMENT_RULES.md`.

Базу ломать не нужно — нужно развернуть её наружу, в GitHub.

### 1.4 `AgentWrapper/agent-orchestrator` — что именно делает его пригодным для внешних агентов

Разобрал репозиторий по частям. Работает не «магия», а конкретный набор артефактов:

| Артефакт | Что делает | Есть у Lucky? |
|---|---|---|
| `AGENTS.md` как **контракт** | Раскладка репо, точные команды, «где смотреть в первую очередь», конвенции и — главное — **«Hard rules and boundaries»**: явный список «не делай» (не менять bind демона, не править сгенерированный код, не трогать смерженные миграции) | Частично, но с локальными путями и без списка запретов |
| `CLAUDE.md` | Три строки: «иди в AGENTS.md» | Создан в рамках TASK-003 |
| `CONTEXT.md` | Глоссарий домена. Только термины, без решений | Нет |
| `CONTRIBUTING.md` | Протокол «застолби задачу»: комментарий в issue → ждёшь назначения → один issue = один PR | Нет |
| `.github/ISSUE_TEMPLATE/*.yml` (Issue Forms) | Структурированные поля с `validations: required` — репорт нельзя отправить пустым | Один `task.yml` от TASK-003 |
| `.github/pull_request_template.md` | What / Why / How / Testing + чеклист со ссылкой на `AGENTS.md` | Нет |
| Таксономия меток | `P0`/`P1`/`P2`, `comp/daemon`, `comp/cli`, `comp/desktop`, `needs-triage`, `blocked`, `good first issue`, `help wanted` | Стоковые метки GitHub |
| ~16 workflow'ов, **срабатывающих на PR** | Проверки по областям, а не одна общая | Один `deploy.yml` только на push |
| `docs/architecture.md`, `docs/STATUS.md`, `docs/adr/` | «Что уже в main, а что в полёте» + записанные архитектурные решения | Нет |

Отдельно: сам продукт AO (изоляция агентов по git-worktree, обратная связь от CI и ревью) у вас **установлен** — `~/.ao`, версия 0.10.2, поставлен 2026-07-11 — но фактически не заведён: один проект `personal` с путём `D:\Google Drive\Personal`, сессий 0, PR 0. Потенциальный слой на будущее (Этап 7), но для цели **не требуется**.

**Главный вывод сравнения.** Разница между Lucky и agent-orchestrator — не в объёме кода и не в инструментах. У AO **точка входа для агента — GitHub**, и всё нужное доступно оттуда. У Lucky точка входа — ваша файловая система. План целиком про перенос точки входа.

## 2. Целевая картина

```
   вы: идея → ревью → Issue (шаблон + AC) → метка agent-ready
                          │
   ┌──────────────────────┼───────────────────────┬────────────────────────┐
   ▼                      ▼                       ▼                        ▼
ваш Claude Code      ваш ChatGPT           агент участника A       агент участника B
 (ветка в репо)    (ветка в репо)          (форк → PR)             (форк → PR)
   │                      │                       │                        │
   └──────────────────────┴───────────┬───────────┴────────────────────────┘
                                      ▼
                        PR «Fixes #N» → CI: тесты + coverage
                                       + версии + гигиена
                                      ▼
                    метка `agent` стоит?  ──нет──→ ждёт вашего взгляда
                                      │да
                                      ▼
                       автомерж (squash) → master → /next/   (~60 секунд)
                                      ▼
              вы: «выкати 2.0.4 в стабильную» → агент двигает тег stable
                                      ▼
                                     /  → дети
```

Руками вы делаете ровно две вещи: формулируете issue и говорите фразу про stable. Всё остальное — агенты и CI.

## 3. План по этапам

Каждый этап — отдельный issue со своими Acceptance Criteria. Этапы 0–3 делаются локально агентом под вашим ревью (пока нет конвейера, его нечем и создавать). Этапы 4–5 уже стоит провести через сам конвейер — это его проверка. Этап 6 — подключение людей — только после того, как 0–5 работают.

### Этап 0 — Стыковка с идущей работой по TASK-003 (15 минут)

**Зачем.** TASK-003 «GitHub External AI Agent Ecosystem» **выполняется прямо сейчас** другим агентом в том же каталоге. Этот план не должен трогать его файлы, пока он не завершён, иначе два агента передерутся за одно дерево.

**Карта пересечений:**

| Артефакт TASK-003 | Отношение к плану | Что с ним делать |
|---|---|---|
| `CLAUDE.md`, `.cursorrules`, `.windsurfrules`, `.github/copilot-instructions.md` | **Совпадает** с Этапом 1 | Оставить; Этап 1 только выверяет, что они ссылаются на обновлённый `AGENTS.md` |
| `.github/workflows/agent-ci.yml` | **Совпадает** с Этапом 2 — единственное место, где появляется триггер `pull_request` | Оставить, на Этапе 2 расширить джобами `version-check` и `hygiene`, переименовать в `ci.yml` |
| `.github/ISSUE_TEMPLATE/task.yml` | **Пересекается** с Этапом 4; полей мало, AC не обязательное поле | Оставить, на Этапе 4 заменить на `feature.yml` / `bug.yml` / `chore.yml` |
| `.github/workflows/sync-tasks.yml` | **Противоречит**: закрепляет markdown-трекер, который Этап 4 убирает | Дать доехать, затем удалить на Этапе 4 |
| `tests/github-agent-ecosystem.test.mjs` | **Частично противоречит**: проверяет существование `tasks/` | Дать доехать, на Этапе 4 переписать проверки под GitHub-трекер |

**Что делать.**

1. Дождаться коммита TASK-003. Не начинать Этап 1 на грязном дереве.
2. Зафиксировать точку старта: `git status --short` пуст.
3. Закрыть issues #1 и #2 (задачи `RELEASED` с 2026-07-28), в комментарии — ссылка на релиз.
4. Открыть issue на этот план и пометить, что он **надстраивает** TASK-003, а не отменяет: TASK-003 даёт адаптеры агентов и проверку на PR, план добавляет автомерж, два канала прода, приватность, перенос трекера и модель доступа для участников.

**Готово, когда**: TASK-003 закоммичен, дерево чистое, открытых issue про сделанное нет.

### Этап 1 — Контракт репозитория (~2 часа)

| `CLAUDE.md`, `.cursorrules`, `.windsurfrules`, `.github/copilot-instructions.md` | По 3–5 строк: «Правила — в `AGENTS.md`, прочитай до первой правки» (уже созданы в TASK-003, выверить) |

| `docs/ui-rules.md` | Перенести UI/UX-часть из `DEVELOPMENT_RULES.md` (тач-таргеты ≥64px, дизейбл Back на индексе 0, модалки 85vh/92vh, 100% английский в UI). `AGENTS.md` ссылается сюда |

Черновик раздела «Жёсткие правила и границы» — то, чего сейчас критически не хватает:

```markdown
## Жёсткие правила и границы

- Никогда не пуш в `master` напрямую — ни агентом, ни человеком. Только ветка + PR.
- Один issue — один PR. Не смешивать несвязанные правки.
- `engine/*` не импортирует DOM и не обращается к `window`. Логика проверяется юнит-тестами.
- Версия задаётся только в `package.json`. Остальные места генерируются через
  `npm run version:sync`. Не править `APP_VERSION`, `CACHE_NAME` и версию
  в `manifest.json` руками.
- Не создавать новые файлы в корне репозитория. Документы — в `docs/`.
- UI игры — только на английском. Русский текст в интерфейсе недопустим.
- Не понижать пороги покрытия в `package.json`, чтобы «прошёл» CI.
- Не трогать `docs/releases/` и `docs/walkthroughs/` — это архив.
- Не менять `.github/workflows/deploy.yml`, `promote-stable.yml` и `auto-merge.yml`
  без явного указания в задаче: они управляют тем, что видят дети.
- Не ставить метку `agent` на собственный PR — она даёт право на автомерж.
- Не коммитить `node_modules/`, локальное состояние, токены.
```

**Готово, когда**: `rg 'file:///|D:\\SD'` по репозиторию не находит ничего; агент, которому дали только ссылку на репо, отвечает на «как запустить тесты» и «куда класть новый движок» без уточнений.

### Этап 2 — PR-конвейер: проверки и автомерж (~2 часа)

**Зачем.** Сейчас «зелёный CI до мержа» невозможен: проверки бегут только после push в `master`, когда уже поздно. А раз вручную не пушит никто, PR становится единственным путём для всех — и это упрощает контракт до одной строки.

**Что делать.**

1. **`.github/workflows/ci.yml`** (на базе `agent-ci.yml` из TASK-003), триггер `pull_request` + `push: master`. Джобы:
   - `test` — `npm ci`, `npm run test:coverage:gate`
   - `version-check` — версия во всех местах совпадает с `package.json` (см. Этап 3)
   - `hygiene` — нет новых файлов в корне (allow-list), нет `file:///`, нет `node_modules/` в диффе

   **Важно для будущих участников**: этот воркфлоу обязан быть безопасным для PR из форков. Триггер строго `pull_request` (не `pull_request_target`), никаких секретов в этих джобах, права токена — только чтение. Тестам секреты не нужны, так что ограничение бесплатное.

2. **`.github/workflows/auto-merge.yml`** — привилегированный воркфлоу, запускается по `workflow_run` от `ci.yml` (то есть в контексте базового репозитория, где доступны права на запись). Логика: PR имеет метку `agent`, все проверки зелёные → `gh pr merge --squash --delete-branch`.

   Автомерж делается воркфлоу, а не встроенной функцией GitHub, сознательно: встроенный auto-merge осмыслен только вместе с branch protection, а она на приватном репозитории Free-плана может быть недоступна. Воркфлоу работает на любом плане.

3. **Метка `agent` = разрешение на автомерж.** Это ключевой элемент модели доступа. Ставить метки может только тот, у кого права `Triage` и выше, — значит, PR от приглашённого участника не уедет в `master`, пока кто-то доверенный его не пометит. Бесплатный аналог required review. Для ваших собственных агентов метку ставит шаблон/сам агент при создании PR по вашему issue.

4. **Скорость.** Путь «PR открыт → `/next/` живой» = CI ~25 с + автомерж + деплой ≈ 60 секунд. Это и есть требование «как можно быстрее».

5. **Метки**: `P0`/`P1`/`P2`, `area/engine`, `area/content`, `area/ui`, `area/ci`, `area/docs`, `needs-triage`, `blocked`, `agent-ready`, `agent`, `good first issue`.

6. **Учёт минут Actions.** На приватном репозитории Free-плана лимит 2000 минут в месяц. При прогоне ~25 секунд это несущественно, но `deploy.yml` не должен запускаться на PR — только на `master` и на промоут.

**Готово, когда**: тестовый PR с меткой `agent` мержится сам после зелёного CI и удаляет ветку; PR без метки ждёт; ни один путь в `master` в обход PR не используется.

### Этап 3 — Приватный исходник, публичный сайт, два канала (~день; самый рискованный)

**Зачем.** Три требования сходятся в одну работу: свобода всё переиграть, публичный сайт для детей, два канала прода.

**Целевая схема.**

| Репозиторий | Видимость | Содержимое |
|---|---|---|
| `usov-andrey/lucky-learning-world-src` | **приватный** | Всё: код, тесты, `docs/`, issues, история, брифы. Здесь вы вольны снести issues, переписать историю, переиграть версии |
| `usov-andrey/lucky-learning-world` | публичный | **Только собранный сайт.** Ни тестов, ни `docs/`, ни брифов, ни `scripts/`. Полностью генерируемый — его тоже можно в любой момент перезалить с нуля |

Имя публичного репозитория выбрано так, чтобы **URL не изменился**: `https://usov-andrey.github.io/lucky-learning-world/` — уже разосланные в LINE ссылки продолжают работать. Для этого текущий репозиторий переименовывается в `…-src` (GitHub держит редирект, локально нужен `git remote set-url`), после чего под освободившимся именем создаётся новый публичный.

| Адрес | Что | Как обновляется |
|---|---|---|
| `https://usov-andrey.github.io/lucky-learning-world/` | **stable** — то, во что играют дети | Только когда агент двигает тег `stable` по вашей команде |
| `…/next/` | **next** — текущий `master` | Автоматически при каждом мерже, ~60 секунд |

**Механика.** Источник истины один — дерево в корне приватного репо. Никаких копий в git.

```
deploy.yml (на push в master и на промоут), в приватном репо:
  checkout master        → allow-list файлов → _site/next/
  checkout тега stable   → allow-list файлов → _site/
  git push _site → публичный репо, ветка main   (токен SITE_DEPLOY_TOKEN)

публичный репо: Pages = «Deploy from branch», main, /
```

`promote-stable.yml` (`workflow_dispatch`, вход `version`): проверяет, что тег `v<version>` существует и его CI был зелёным → переставляет тег `stable` → запускает `deploy.yml`.

**Allow-list публикации** — что уезжает наружу: `index.html`, `app.js`, `styles.css`, `themes.css`, `sw.js`, `manifest.json`, `telemetry.js`, `engine/`, `content/`, `assets/`, `pokemon/`, `.nojekyll`. Всё остальное остаётся приватным.

**Токен**: fine-grained PAT с правом `Contents: Write` **только** на публичный репозиторий, в секретах приватного как `SITE_DEPLOY_TOKEN`. Дату истечения — в календарь.

**Сопутствующие работы этого этапа (без них каналы не поедут):**

1. **Удалить `v1/` и `v2/`** из git (485 файлов). Перед удалением — тег `archive/v1-v2-snapshot`.
2. **Единый источник версии.** `package.json` — единственная правда. `npm run version:sync` записывает её в `app.js` (`APP_VERSION`), `sw.js` (`CACHE_NAME`), `manifest.json`. Из `index.html` хардкод убрать — подставлять из `APP_VERSION` в рантайме. `npm run version:check` в CI падает при расхождении.
3. **Переписать `scripts/release.mjs`**: убрать глобальную регулярку по `index.html`. Релиз = bump в `package.json` + `version:sync` + тег + запись в `CHANGELOG.md`.
4. **Service Worker и области видимости.** SW, зарегистрированный как `/sw.js`, имеет scope `/` и накроет собой `/next/`. Регистрацию сделать относительной — `register('sw.js', { scope: './' })`. `CACHE_NAME` обязан содержать версию (уже так). Network-first сохраняется.
5. **Переключатель каналов в UI**: в модалке настроек «Try the next version» / «Back to stable». Заменяет самодельную навигацию по `v1/`/`v2/`.
6. **`docs/runbooks/promote-stable.md`** — раз промоут выполняет агент по вашей фразе, процедура должна быть записана в репозитории, чтобы её исполнил любой агент в любой сессии: как проверить, что версия зелёная, как двинуть тег, как убедиться, что `/` обновился, **как откатить** (вернуть тег на предыдущий и передеплоить).

**Риски.** У пользователей уже стоит SW с прежним `CACHE_NAME`, и корень `/` меняет смысл (был «самое свежее», станет «стабильное»). Разово возможен показ старого контента до обновления SW. Смягчение: промоутнуть в `stable` ровно текущую живую версию **до** всех переключений.

**Порядок выполнения строго такой** (иначе сайт ляжет):
1. Поставить тег `stable` на текущий рабочий коммит.
2. Собрать `deploy.yml` с allow-list, публиковать пока в тестовый публичный репозиторий.
3. Убедиться, что тестовый сайт идентичен живому.
4. Переименовать текущий репо в `…-src`, сделать приватным.
5. Создать публичный `lucky-learning-world`, включить Pages, переключить деплой.
6. Проверить, что старый URL работает и отдаёт stable.
7. Только после этого удалять `v1/` и `v2/`.

**Готово, когда**: исходник приватный; сайт публичный по прежнему URL; `/` и `/next/` показывают разные версии; мерж PR меняет только `/next/`; фраза «выкати X.Y.Z в стабильную» двигает `/`; в публичном репозитории нет ни одного `.md`-брифа.

### Этап 4 — Трекер переезжает в GitHub Issues + Projects (~2 часа)

**Зачем.** Это ответ на «дальше начинается строительство велосипедов». `sync-issues.mjs`, `task-new.mjs`, `INDEX.md`, `sync-tasks.yml` — 300+ строк самописного кода, воспроизводящего то, что GitHub умеет из коробки и, главное, показывает наружу — включая агентам чужих людей.

**Что делать.**

1. **Issue Forms** вместо одного `task.yml`:
   - `feature.yml` — Контекст и зачем; **Acceptance Criteria** (по одному на строку, формат `AC-1: …`, `required`); Затронутые области (dropdown → метка `area/*`); Как проверить; Ограничения и что трогать нельзя
   - `bug.yml` — шаги воспроизведения, ожидаемое/фактическое, канал (`/` или `/next/`), устройство
   - `chore.yml` — техдолг, документация, CI
   - `config.yml` — ссылки на `AGENTS.md` и `CONTRIBUTING.md`
2. **В хвост каждого шаблона — фиксированный блок «Контракт агента»**: прочитай `AGENTS.md`; ветка `issue-<N>-<slug>`; прогони `npm run test:coverage:gate`; добавь тест с тегом `@issue <N>`; открой PR с `Fixes #<N>`; не трогай перечисленное в «Жёстких правилах».
3. **GitHub Project (v2)**: `Backlog` → `Ready for agent` → `In progress` → `In review` → `Done`. Метка `agent-ready` = «сформулировано достаточно, агент берёт без вопросов».
4. **Definition of Ready** (в `CONTRIBUTING.md`): есть хотя бы один `AC-*`, указана область, указано как проверить результат, нет открытых вопросов к вам. Без этого `agent-ready` не ставится.
5. **Миграция**: три файла `tasks/*.md` → issues с полным телом и AC. TASK-001 и TASK-002 закрыть как выполненные. «Backfill AC tags for legacy test suites» — открыть как живой issue. TASK-003 закрыть как поглощённый этим планом.
6. **Удалить**: `tasks/`, `scripts/sync-issues.mjs`, `scripts/task-new.mjs`, `.github/workflows/sync-tasks.yml`, корневой `ACCEPTANCE_CRITERIA.md`, корневые `implementation_plan.md` и `walkthrough.md`. Из `package.json` убрать `task:new` и `task:sync`.
7. **Сохранить как архив**: `docs/plans/`, `docs/walkthroughs/`, `docs/releases/` — не удалять, но перестать требовать по каждой задаче. История релизов дальше собирается из заголовков PR в `CHANGELOG.md`.
8. **Тег связи с задачей** в тестах меняется с `@task TASK-XXX` на `@issue <N>`. Старые теги оставить.

**Готово, когда**: `tasks/` нет; новый issue создаётся через форму и содержит AC в теле; внешний агент по одной ссылке на issue получает всё нужное, ничего не спрашивая.

### Этап 6 — Подключение других пользователей GitHub и их агентов

**Зачем.** Заявленная цель следующего шага: приглашённые участники вносят вклад своими агентами. Делать это можно только после того, как Этапы 0–5 работают, иначе чужие агенты попадут в репозиторий без контракта, без CI на PR и с прямым доступом к тому, во что играют дети.

**Модель доступа — три уровня, без платного плана:**

| Роль | Права GitHub | Что может | Что не может |
|---|---|---|---|
| Владелец | Admin | Всё | — |
| Доверенный участник | `Triage` (или `Write`, если нужен пуш веток) | Ставить метки, в том числе `agent` → разрешать автомерж; вести триаж issues | — |
| Приглашённый участник | `Read` | Форкнуть приватный репозиторий, работать своим агентом, открыть PR из форка, обсуждать issues | Пушить в `master`, ставить метки, запускать автомерж |

Ключ модели: **метка `agent` — единственный ключ к автомержу**, а ставить её может только `Triage`+. Приглашённый участник и его агент физически не могут отправить код к детям и даже в `master` без действия доверенного человека. Это даёт эффект required review бесплатно.

**Что нужно настроить.**

1. Включить в приватном репозитории **разрешение форков** (иначе схема с `Read` не работает).
2. Проверить, что `ci.yml` безопасен для PR из форков: триггер `pull_request`, никаких секретов, токен только на чтение. Если этого не сделать, чужой PR сможет добраться до `SITE_DEPLOY_TOKEN`. Это самая опасная ошибка во всём плане — вынести отдельным AC.
3. Раздел «Для приглашённых участников» в `CONTRIBUTING.md`: как форкнуть, как настроить своего агента на `AGENTS.md`, как застолбить issue, чего ожидать по срокам ответа.
4. Метки `good first issue` и `help wanted` начинают работать по назначению — как в `agent-orchestrator`.
5. `CODEOWNERS` — как документация ответственности по областям (принудительное ревью на Free-плане не заработает, но файл полезен агентам как карта).
6. Решить, что делать с приватностью при росте числа участников: чем их больше, тем меньше смысла в приватности и тем выше цена административных ограничений Free-плана. Порог для пересмотра — примерно 3–5 активных участников.

**Готово, когда**: приглашённый участник с правом `Read` форкает репозиторий, его агент открывает PR, CI на форк-PR проходит без доступа к секретам, вы ставите метку `agent`, PR автомержится, изменение появляется на `/next/`.

## 6. Что этот план сознательно НЕ делает

- Не рефакторит игровой код (`app.js` — 55 КБ, `index.html` — 29 КБ). Отдельная задача, и её как раз стоит отдать агентам **после** запуска конвейера.
- Не наполняет `harness/skills`. Это работа по workspace, не по Lucky.
- Не вводит сборку/минификацию: скрывать код не требуется, а zero-build — опора всей работы с агентами.
- Не заводит AO как обязательный слой.
- Не трогает `docs/releases/`, `docs/walkthroughs/`, `docs/plans/` — исторические артефакты сохраняются.
