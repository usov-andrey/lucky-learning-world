## 3. Архитектурное решение для быстрого и безопасного переноса

На первом релизе не объединять обе игры в один большой `app.js`. Использовать **тонкий хаб и два изолированных игровых модуля**:

```text
lucky-learning-world/
├── index.html              # два главных входа для Лаки
├── app.js                  # только хаб, навигация и очистка старого SW
├── styles.css              # дизайн хаба
├── games/
│   ├── math/               # согласованный снимок math-monster
│   └── spelling/           # Game + Learn + Test с Page 22
├── tests/
│   └── integration/        # проверки хаба, ссылок и контентных контрактов
└── docs/
    └── handoff/            # состояние переноса между агентами
```

Преимущества:

- можно перенести рабочие приложения, а не повторно реализовывать их поведение;
- Math и Spelling не делят DOM, глобальное состояние и CSS;
- два агента работают параллельно в разных каталогах без конфликтов;
- ошибку одного режима легче локализовать и откатить;
- позже общие экран, профиль и коллекцию можно выделить отдельно, не задерживая игру на сегодня.

## 4. Неподвижные продуктовые правила

Каждый агент обязан соблюдать их до начала изменений:

- Игрок — Лаки, 10 лет; это семейная игра, не публичный edtech-продукт.
- В Math доступны только таблицы ×6..×10 и уже существующие в `math-monster` Mix/collection/parent функции. Addition, division и ×2..×5/×11..×12 не входят в релиз.
- Голос в Math обязателен; читаемый текст дополняет голос.
- Неверный ответ не наказывается: правильный ответ объясняется и озвучивается, прогресс не откатывается, нет `lost`, `failed` и жёсткого game over.
- Touch targets — не менее 64×64 px.
- Spelling содержит три явно разделённых режима: Game, Learn и Test.
- Буквенные плитки используются в Game и не подменяют механику Learn/Test.
- Page 22 — default/current lesson 26–27 июля 2026 года. Поведение после 27 июля требует отдельного решения владельца.
- Vanilla JS и нативные ES modules; без bundler и runtime-зависимостей.
- Исходные репозитории во время переноса read-only. Все содержательные изменения выполняются и коммитятся только в `lucky-learning-world`.

Первым коммитом реализации следует синхронизировать `AGENTS.md` проекта назначения с этими правилами. Его текущее описание ×2..×12, дополнительных предметов и приложения для одноклассников слишком широко для новой цели.

## 5. Storage и сохранение прогресса Лаки

Все три live-сайта находятся на origin `https://usov-andrey.github.io`, поэтому `localStorage` общий для них независимо от пути URL.

Правила переноса:

1. Math продолжает использовать исходный `storage.js` и стабильный namespace `lmm3s:`. Не переносить математический прогресс в общий объект хаба и не переименовывать ключи.
2. До cutover создать диагностический snapshot ключей `lmm3s:*` на целевом iPad и проверить загрузку теми же fixture-тестами, но не печатать персональные данные в CI-логах.
3. Ключ `luckyLearningWorld_v1` оставить отдельным legacy-состоянием хаба; новая математика не должна его читать или перезаписывать.
4. Для Spelling сохранить preference keys `lucky-spelling-language` и `lucky-spelling-theme`, чтобы настройки с прежнего сайта продолжили работать.
5. Reset в Math удаляет только собственный namespace. Нужен тест, что spelling и hub keys остаются нетронутыми.

## 10. Gate перед production deploy

Production deploy запрещён, если выполняется хотя бы одно условие:

- Math tests меньше исходных 87 без письменного объяснения удалённых тестов;
- Page 22 содержит не 18 слов или не тот порядок;
- отсутствует хотя бы один из режимов Game, Learn или Test;
- в Test видно целевое слово;
- на iPad нет звука после tap;
- `lmm3s:` прогресс не загружается или перезаписывается новым пустым state;
- активный старый service worker отдаёт предыдущий `app.js`;
- корневой `node --test` красный.

Даже при всех зелёных проверках production deploy запрещён до явного подтверждения владельца после просмотра тестовой версии.

## 11. Rollback

1. Перед merge отметить последний рабочий commit текущего хаба тегом или записать SHA в handoff.
2. Не удалять `math-monster` и `lucky-spelling-test`: они остаются рабочими fallback URL.
3. При критической проблеме сделать revert cutover-коммита и повторно задеплоить `master`; не переписывать историю `git reset --hard`.
4. Не удалять и не мигрировать назад `lmm3s:` — rollback должен снова увидеть тот же прогресс.
5. После rollback записать канал, устройство, последние действия и наблюдаемое поведение.

## 12. Формат handoff каждого агента

Каждый агент завершает работу сообщением и файлом со следующими полями:

```text
Агент:
Source SHA:
Destination commit:
Изменённые файлы:
Что работает:
Какие тесты запущены и результат:
Что не проверено:
Риски/допущения:
Точный следующий шаг:
```

Оркестратор не принимает результат вида «готово» без списка файлов, test output и commit SHA.
